# First-Wave Platforms

Each of the first five platforms has a default login method that requires no configuration, and administrators can switch to their own developer app under "Configure app". An adapter is only responsible for obtaining credentials and writing them, together with matching renewal parameters, into the corresponding driver's fields; renewal is handled by the driver, and adapters do not call any refresh endpoint, avoiding refreshing the same credential at the same time as the driver. Other platforms and other account types continue to use the native OpenList storage form. connect 4 adds one further non-drive platform, "API upstream (`goapi`)", see [the dedicated section below](#api-upstream-goapi-connect-4).

**Verification status (as of 2026-10-14)**: users have reported that Aliyun Drive, Baidu Netdisk, 123 Cloud Drive and OneDrive logins have passed real-world testing; Google Drive has not yet been tested with a real account. "Verified" here only means that feedback of a successful login with a real account has been received; it does not mean that every account type, reauthorization flow, failure-recovery path, or long-term renewal behavior has been validated. Untested items are left blank. Users are welcome to test Google Drive, own-app login, different account types, and other drivers that OpenList already supports but cloud2api has not yet tested sufficiently, and to submit redacted results or PRs; see [Real-Account Testing and Contribution](../../docs/REAL-ACCOUNT-TEST.en.md#community-testing-and-pull-requests).

When no app configuration has been saved, the platform uses the default method and the page marks it "Default"; after another method is saved under "Configure app", the platform switches to the selected method, and "Restore default" deletes the saved configuration. The adapter writes renewal parameters according to the selected method, and does not infer the token source from whether a field is empty. Reauthorization replaces only the fields in the table above; the mount point, root directory, driver type and other settings are left unchanged.

"Paste token" uses the same token-retrieval method commonly used with the native OpenList form: log in with OpenList's app on the OpenList authorization page api.oplist.org, and once the page shows the refresh token, copy it back. When renewing, the OpenList driver always uses one specific app type for that service (Baidu `baiduyun_go`, OneDrive `onedrive_pr`, Google `googleui_go`), so the corresponding option must be selected on the authorization page; the "Open OpenList authorization page" button on the login page pre-selects it where possible. The token is initialized and verified by the driver when the storage is saved; if it is invalid, this is handled as a failed creation and cleaned up.

## Platform notes

### Baidu Netdisk

- The default "QR code login" uses Baidu's device-code authorization: the login page shows a QR code generated by Baidu; scan it with the Baidu Netdisk app and confirm. Alternatively, open `https://openapi.baidu.com/device` in a desktop browser and enter the code shown on the page.
- The QR code uses the public app pre-filled by "Baidu Netdisk - Manual login" on api.oplist.org (AppKey `NqOMXF6XGhGRIGemsQ9nG0Na`). This AppKey and SecretKey are written into the storage, and the driver uses them to renew directly with Baidu, without going through api.oplist.org. It is published publicly by the OpenList authorization tool and is not owned by this project; if it is revoked or rate-limited, switch to one of the two methods below.
- "Paste token": on api.oplist.org select "Baidu Netdisk - Verify login (OAuth App)" and check "Use parameters provided by OpenList", obtain the refresh token and paste it; the driver renews through the online authorization service.
- "Own app": create an app on the [Baidu Netdisk Open Platform](https://pan.baidu.com/union), obtain the AppKey (client_id) and SecretKey (client_secret), and register the callback address `…/api/connect/oauth/callback` shown on the login page; if it cannot be registered, set the callback address to `oob` and, after authorization, paste the authorization code shown on the Baidu page back into the login page.
- New storages use the driver's other defaults (download interface `official`, etc.); modify them in the native OpenList form if they need to be adjusted.

### Aliyun Drive

- Only the open-platform driver `AliyundriveOpen` is integrated. By default it uses the OpenList online authorization service for QR-code login, writing `use_online_api=true` and that service's renewal address; own-app mode writes `use_online_api=false` and the app parameters. The two kinds of credentials are not interchangeable.
- The QR code is an image provided by Aliyun Drive and is displayed directly on the page. Polling distinguishes six states: waiting, scanned, confirmed, cancelled on the phone, expired, and network error. On a network error, polling continues; an expired QR code is dimmed and can be refreshed; cancelling on the phone ends the session and it must be started again.
- A new storage mounts the resource library (driver default `drive_type=resource`); modify it in the native form to use a backup drive.

### 123 Cloud Drive

- It uses the `123Pan` driver for ordinary accounts and does not require a developer app. This is a different integration from the `123 Open` open-platform driver, and credentials cannot be mixed between them.
- The login page does not itself call 123's login endpoint; the account and password are verified by the driver when the storage is saved, so as to avoid repeated logins triggering risk controls. The upstream states that this driver is no longer actively maintained.

### OneDrive

- Default "paste token": "Open OpenList authorization page" on the login page pre-selects "OneDrive - Personal (OAuth App)" and checks "Use parameters provided by OpenList"; click "Get Token" to log in with the Microsoft account, then copy the refresh token shown on the page and paste it back into the login page. Both personal accounts and work or school accounts select this option, and the driver always uses `onedrive_pr` when renewing. Work or school accounts may require consent from the organization's administrator.
- "Own app": register an app in Microsoft Entra, choose "Accounts in any organizational directory and personal Microsoft accounts" for supported account types, select Web as the platform, fill in the callback address shown on the login page as the redirect URI, and create a client secret under "Certificates & secrets".
- Only global-region personal accounts and work or school accounts are covered. 21Vianet, US Government, the German region and SharePoint use the native form; a reauthorization request against such a storage is rejected. A new storage writes `region=global` and `is_sharepoint=false`.

### Google Drive

- Default "paste token": the login page opens api.oplist.org; select "Google Drive OAuth2 (OAuth App)", read the Google authorization explanation that pops up and check "Use parameters provided by OpenList", click "Get Token" to log in with the Google account, and copy the refresh token and paste it back into the login page. No option is pre-selected here, so as not to skip the Google explanation on the authorization page.
- "Own app": in the Google Cloud console, enable the Google Drive API, configure the OAuth consent screen, create an OAuth client of type "Web application", and register the callback address among the authorized redirect URIs. When the consent screen is in "Testing" status, the refresh token expires after 7 days. Google only returns a refresh token on the first authorization, so the authorization request carries `prompt=consent`.
- Only "My Drive" is integrated; shared drives have not yet been verified.

## API upstream (goapi, connect 4)

`goapi` is not a cloud drive: it connects **another goapi service** (for example cloud2api on another machine) as a storage. Select this platform in the connect wizard, fill in the remote service's address and API Key, and the new GoAPI storage driver stores these values and uses them to access the upstream. The adapter only writes them into the driver's fields; cloud2api does not handle either value. Pairing acceptance testing in an isolated environment covered trash restore, upload receipts and byte consistency, bounded hop loops, and the passwordless administrator handoff and return flow. Third-party generic GoAPI/Gokapi is still unsupported; these tests do not mean that all real remote accounts or drive uploads have been fully verified. The record table below only records real cloud-drive account tests.

- **Protocol restriction**: only the remote service's cloud2api `/v1` layered protocol is supported, and no generic REST compatibility is provided — this is not a way to connect any arbitrary GoAPI/Gokapi cloud-drive service. The flat upload API of the Gokapi-compatible layer (`/api/files/add`, `/api/chunk/*`, etc.) is not treated as an upstream protocol and is unsupported.
- **List caching**: list results may lag by up to the cache expiration time in the storage configuration (about 30 seconds by default); stat/Get and typed operation results are freshly live, and a manual refresh is enough to update the list when the latest version is needed.
- **Operation scope**: list/stat are proxied streaming reads; mkdir/move/delete are permitted according to the actual permissions of the peer's Key, and when the peer refuses, the error is returned unchanged; copy is completed via OpenList's transfer fallback. The entire storage's visible scope is the drives, root directory and permissions granted by the peer's Key.
- **Upload and receipts**: uploads require a known length (Content-Length); support for zero-byte and multipart is a planned item and is subject to test confirmation. Before declaring success, the upstream receipt's path, size, CRC-64 and SHA-256 are strictly checked; when the result is unknown, mismatched or missing, only "unconfirmed" is reported — no claim of rollback and no blind retry.
- **Hop protection (explicit capability negotiation)**: the peer must explicitly declare the **relay hop limit** capability in `/v1/me` (field `relay_hop_limit`, whose value must equal 4); the driver allows connection only after the check passes. Older peers that lack this capability or declare a different value are always rejected; upgrade the peer first if necessary. Mixed-version peers may drop the hop header when forwarding, so loops cannot be bounded by request headers alone; explicit negotiation is therefore required. Once the check passes, the request header `X-GoAPI-Hop` (an integer 0–4) propagates hop by hop with each request along cloud2api → OpenList → GoAPI driver → peer service; values greater than 4 or of an invalid format are rejected. No database migration is performed, and no persistent instance ID or topology record is introduced; on the upstream side, patch 0003 makes the relay loop terminate at the hop limit instead of hanging.
- **System directories (`system_ns`)**: after a successful initialization probe, the driver generates one random 128-bit system namespace for that storage and saves it with the storage (kept across reauthorization; the wizard has no input for it and introduces no new credentials). The virtual paths `/.c2a-trash` and `/.relay` map to the storage-private ordinary directories `.goapi-system-<ns>-<storage ID>-trash` / `-relay` under the configured root directory. Do not manually modify, copy or empty these directories on the peer, or the virtual aliases will dangle. Addressing boundaries: the physical aliases are not directly addressable in the virtual view; the virtual `/.c2a-trash` and `/.relay` are by design for internal use by the gateway and the native admin console; the reserved-path guard for external access via cloud2api `/v1` is unchanged.
- **Compatibility boundary**: cloud2api makes no promise that this driver is compatible with all goapi implementations: it only connects to cloud2api `/v1` upstreams that support the `/v1` semantics described above, receipt verification and the declared hop protection; older `/v1` instances are not automatically compatible. No fixed deployment topology is claimed.

## Callback address and HTTPS (own app only)

Microsoft and Google only accept HTTPS callback addresses, with the exception of `localhost`. When OpenList is only reachable over a LAN HTTP address, there are two approaches:

1. Access OpenList through an HTTPS reverse proxy, and set `site_url` in the OpenList configuration; the login page will then give the full callback address based on it.
2. Register `http://localhost:5244/api/connect/oauth/callback` in the app. After authorization completes, the browser will redirect to a localhost address that cannot be opened; copy the full address from the address bar and paste it into the "Callback address will not open" input field on the login page. An authorization code can be used only once and must match the state of the current login session.

The default methods (QR code, paste token) do not require a callback address.

## Example adapter

`example-openlist` connects to another OpenList (upstream `OpenList` driver) with an account and password, and is registered only under the `loginsdk_example` build tag, so it does not enter the production image. It is a reference implementation for contributors and the test vehicle for `scripts/e2e.sh`, and it can exercise creation, read/write, reauthorization and the various failure paths without any cloud-drive account.
